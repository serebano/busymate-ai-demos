# `ghost` — The Meridian Line, a real Ghost CMS publication

**Live: <https://ghost.demo.busymate.ai>**

The playground's third **dynamic** demo (after `woo` and `wordpress`) and the first on Ghost —
a genuine Ghost install for an independent print-and-digital magazine covering makers, small
manufacturing and local economies (busymate-devtools#2979, program #2899).

**The Meridian Line is an invented publication** — a three-person editorial outfit. It is not a
real magazine, takes no real subscriptions or payment. Every photograph is a freely licensed
Wikimedia Commons file, credited in [`seed/IMAGE-CREDITS.md`](seed/IMAGE-CREDITS.md). It runs
Ghost's own bundled **Casper** theme (Ghost's real flagship theme, not a custom build) plus
Ghost's native **Members/Portal** for reader accounts.

## Why this demo exists (distinct from `wordpress`)

Ghost has no plugin runtime like WordPress — there is no generated per-tenant plugin to install.
The integration is our **universal embed** (`embed/v1.js`) wired through Ghost's own **Code
Injection** (Settings → Code injection → Site Header, for the floating widget on every page)
plus an **inline** placement: an HTML card embedding the same `/support/<slug>` iframe the
widget uses, placed on the About and Contact pages — the same shape as `wordpress`'s
`[bmai_assistant]` shortcode, authored as native Ghost content instead of PHP.

## The full-feature checklist, as built here

| Capability | How |
| --- | --- |
| Grounded chat | Knowledge published from the magazine's own About/Contact/article copy (`publish_tenant_runtime` `knowledge_sources`) |
| WebMCP page tools | `list_articles`, `search_content`, `get_contact_info`, `who_is_signed_in`, `subscribe_newsletter` — registered client-side via a small script in Code Injection, same pattern as `wordpress`'s page tools |
| An MCP server | [`backend/index.mjs`](backend/index.mjs) — the shared, dependency-free `sites/_shared/backend/mcp-identity-server.mjs`, fed this demo's tools ([`backend/tools.mjs`](backend/tools.mjs)) reading Ghost's own public Content API, registered as the tenant's `meridian` connector |
| Identified sign-in | The one provided demo member, `nadia@ghost.demo.busymate.ai` — a REAL Ghost Member created via the Admin API (not just a mock object) — signs in through the shared server's own `/api/identity/login`, minting an ES256 launch proof the same way `scan`/`web` do |
| Hand-off to a person | The platform's own hand-off; say "I'd like to talk to someone" in the chat |
| Docs + code links | `demo.json` → `docs`/`code`, validated by `scripts/gen-manifest.sh` |
| Native Ghost feature shown honestly | Ghost's own Members/Portal sign-up widget is live on the site (a REAL Ghost feature) — distinct from and alongside the bmai identity button, documented so a visitor can tell which is which |

## Recreating the site from scratch

1. [`provision.sh`](provision.sh) — containers (Ghost 5 + MySQL 8, own docker network), nginx
   vhost, Let's Encrypt cert. Ghost's own docs mark SQLite (`database__connection__filename`)
   dev-mode only, so this runs Ghost in production against MySQL 8 (Ghost requires MySQL, not
   MariaDB) — same posture as `wordpress`/`woo` against MariaDB for WordPress.
   `security__staffDeviceVerification=false` is required — see the comment in the script.
2. First-run setup over the Admin API (`/ghost/api/admin/authentication/setup/`, which also
   takes the site title): "The Meridian Line", an owner account, then 3 pages + 3 posts authored
   directly via the Admin API (`?source=html`) — using the bundled **Casper** theme (no custom
   theme build). Six credited Wikimedia photos uploaded via `/images/upload/` and attached as
   `feature_image`.
3. Create a **Custom Integration** (Admin API) for a Content API key + Admin API key. The ES256
   identity keypair is generated by the shared backend server itself on first boot
   (`ensureKeypair`), never hand-typed.
4. Build + run [`backend/`](backend) (the MCP + identity server) and register it as a connector
   (Console → MCP connections → probe → classify each tool `public`/`identified` → save).
5. Create the one real Ghost Member `nadia@ghost.demo.busymate.ai` — represented in
   `store.mjs`'s `demoCustomer` (the shared identity server signs a launch proof for this
   profile; a genuinely created Ghost Member is the honest anchor for it).
6. Register the identity provider (Console → End-user identity → Add provider), then
   **"Test identified launch"** to prove all four checks green (config / JWKS / launch refusal /
   publication).
7. Publish branding + `access.allowedOrigins` + `channels.embedOrigins` + `identity.providers`
   (Console → Brand and experience → Advanced JSON — this is where a tenant's full runtime
   config lives, the Console UI's own `publish_tenant_runtime` equivalent).
8. Wire Code Injection (Site Header) with the embed `<script>` tag, the `getIdentity` bridge
   (defined **before** the embed tag — required, the embed captures it once at load), and the
   WebMCP page-tools registration — all via the Admin API's `settings` PUT, not the browser.
9. Add an HTML-card iframe (same `/support/<slug>` src as the widget) to the About/Contact pages
   for the inline placement.
10. **Knowledge — two independent mechanisms, both needed:**
    - The **crawled website** (Console → Knowledge base → Add a knowledge source →
      `https://ghost.demo.busymate.ai`) indexes the live pages (search/discovery layer). This
      published cleanly on the FIRST publish.
    - **Chat retrieval** reads a *separate*, hand-authored fact/reference library
      (`Brand and experience → Advanced JSON → knowledge.sources[]`, `kind: fact|howto|
      reference|glossary`, plain `content` strings — NOT the crawled pages, and NOT arbitrary
      client-invented ids: the server rejects an unrecognized id with `422
      invalid_resource_selection`). The ONLY ids that work are ones the checklist widget itself
      hands you back — assign them on **Console → Knowledge, tools, and behavior** (tick each
      "Source: …" checkbox: those ARE the crawled-page chunks, now offered as citable knowledge)
      and Save draft → Run preflight → Publish *there*. `release.requiredScenarios` also needs
      `identified-launch` and `knowledge-citations` added once those features are enabled, or
      preflight refuses with "must include enabled-feature scenarios: …".
    - `Save draft` on `Brand and experience` after editing Advanced JSON does NOT always bump
      the revision number if the previous save is still in flight — verify the draft actually
      contains your edit (re-open Advanced JSON) before clicking Publish, or the wrong revision
      ships.

### Ghost Admin API gotchas hit live (2026-09-15)

- **`security__staffDeviceVerification=false`** — Ghost 5.next emails a one-time code on the
  first admin session login from a new device; with no SMTP relay (and DO's default outbound
  :25 block) the request hangs ~2 min then 500s. This env var is the documented escape hatch.
- **Session-cookie auth requires `X-Forwarded-Proto: https`** — calling the Admin API over
  plain `http://127.0.0.1:PORT` (bypassing the TLS-terminating vhost) with a `url` config of
  `https://…` makes Ghost silently withhold the `Set-Cookie` header entirely. Send the header on
  every session-auth call (login, settings PUT, images/upload).
- **A new Custom Integration's Admin API key works over JWT immediately; the Content API key
  needs the integration created via a session-authed POST**, not the Integration's OWN JWT (the
  Integration doesn't exist yet to sign with).
- **The public Content API lives under `/ghost/api/content/`** — a blanket `location ^~ /ghost/
  { return 404; }` (meant to close the Admin UI) catches it too; carve out
  `/ghost/api/content/` as its own, more specific `location` first.

## Hardening

Same posture as `wordpress`/`woo`: `/ghost/` (Admin UI) 404s publicly — administered only
through the Admin API from the box's own docker network. The Content API + Members/Portal stay
open (the point of the demo); the front end is public.
